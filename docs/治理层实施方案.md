## 0. 结论先行：治理层是什么、不是什么

```
Agent ──MCP(streamable HTTP)──▶ [ 治理层 ] ──MCP(stdio/HTTP)──▶ 上游 MCP Server
                                   │
                                   ├─ ① 租户解析（谁在调）
                                   ├─ ② 限流（能不能调，令牌桶 + Lua）
                                   ├─ ③ 审计（调了什么，脱敏落库）
                                   └─ ④ 指标（快不快、错多少，Prometheus）
```

**它是**：一个对 Agent 而言"就是 MCP Server"、对上游而言"就是 MCP Client"的**透明代理**，治理逻辑挂在中间的 ASGI 协议层。

**它不是**：
- ❌ 自定义 HTTP 接口（现在 `govern/proxy.py` 的 `POST /api/v1/call_tool`）—— `langchain-mcp-adapters` 只会说 MCP 协议，接不上
- ❌ 一个 `asyncio.sleep(0.05)` 的假后端
- ❌ 重新实现 MCP 协议栈（转发用官方 `mcp` SDK，你只在协议层"插一脚"）

## 1. 为什么是「路线 B（ASGI 中间件）」而不是别的

| 路线 | 做法 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| A | 在 `FastMCP.call_tool` 里做治理 | 最简单，一天能跑 | 只能治理 `tools/call`；`tools/list`、`resources`、`prompts` 都漏；治理逻辑和业务代码耦合 | 适合快速验证 |
| **B（本方案）** | **ASGI 中间件拦 `/mcp` 的 JSON-RPC，转发交给代理 app** | **协议层透明**：所有方法都能治理；**限流在进入上游前就拒绝**（不浪费一次转发）；和真实网关（ContextForge）同构 | 要自己解析 JSON-RPC；要用**纯 ASGI 中间件**（`BaseHTTPMiddleware` 读 body 会卡住流） | ✅ 选它 |
| C | 自造 HTTP 接口 | 无 | Agent 用不了 | ❌ 放弃 |

**关键设计取舍（面试会问「为什么不用 A」）**：
> 因为限流要在**工具执行前**生效，而且 `tools/list` 也会被滥用（无限刷 list 一样打爆上游）。挂 `call_tool` 只能看你记得的那一个入口；挂在协议层，任何 `method` 都必须过同一道闸。

**同时也保留了 A 的能力**：转发逻辑（MCP Client 连上游）是必须写的，跟中间件不冲突。

> 📌 关于你之前问的另外两个选择，本方案先定成这样（都是可替换的局部决策，不动架构）：
> - **上游连接**：先做 `stdio` 子进程（可 CI、可单测），`--transport http` 留参数位
> - **审计存储**：SQLite + SQLAlchemy 2.x async 起步（只改 `DATABASE_URL` 就能换 Postgres）

## 3. 协议与数据契约（先定死，后面都靠它）

### 3.1 上游/下游的 MCP 消息形状

```jsonc
// 1) 握手
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"agent"}}}

// 2) 列工具（要治理：防刷）
{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}

// 3) 调工具（治理重点）
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"query_order","arguments":{"order_id":"A123"}}}
```

**中间件只做 3 件事**：取 `method`；若 `method == "tools/call"` 取 `params.name` 与 `params.arguments`；其余方法只做限流与指标，不碰参数。

> ⚠️ `tools/call` 的入参字段是 `arguments`（不是 `args`、不是 `params`）。你现在的 `proxy.py` 用的是 `args`，这是"自己发明的协议"，也是它接不上 Agent 的直接原因之一。

### 3.2 租户从哪来

| 方式 | 写法 | 说明 |
|---|---|---|
| 起步（本方案） | `X-Tenant-Id: t1` header | 简单、可测；缺省 `anonymous` |
| 生产 | 从 `Authorization: Bearer <jwt>` 解出 `sub/tenant` | 只换 `tenant.py`，中间件不动 |

### 3.3 审计表（SQLAlchemy 模型 = DDL）

```python
class ToolAudit(Base):
    __tablename__ = "tool_audit"
    id          = mapped_column(Integer, primary_key=True)
    tenant      = mapped_column(String(64), index=True)
    tool        = mapped_column(String(128))
    args_digest = mapped_column(String(64))    # sha256(canonical(args))
    args_keys   = mapped_column(Text)          # '["order_id"]' —— 只存 key
    args_size   = mapped_column(Integer)       # 字节数
    status      = mapped_column(String(32))    # ok / rejected_ratelimit / upstream_error / upstream_timeout
    duration_ms = mapped_column(Integer)
    created_at  = mapped_column(DateTime(timezone=True), index=True)
    # 复合索引：(tenant, tool, created_at) —— 查「租户 A 今天调了几次 query_order」
```

**脱敏规则（必须写进 README，也必须有测试）**：

- ❌ 不存 `arguments` 原文 —— 可能含手机号、地址、订单号
- ✅ 存 `args_keys`（字段名列表）、`args_size`、`args_digest`（用于"同一次调用是否重复"）
- ✅ 需要排障时，用 digest 反查日志里同 digest 的条目，而不是存明文

## 4. 分阶段实施（每阶段：写什么 → 怎么测 → 怎么验收）

### P0 · 代理骨架（半天）

**目标**：Agent 能经治理层调到上游工具；`tools/list` 与直连**字节一致**。

**要写**
- `govern/app.py`：用 `mcp.server.fastmcp.FastMCP` 起一个 server；`lifespan` 里建**上游 `ClientSession`**（`mcp.client.stdio.stdio_client`）
- 用 `FastMCP.add_tool()` **动态注册**上游的每个工具（`list_tools()` → 逐个 `add_tool`），`call_tool` 转发到上游
- `govern/settings.py`：`upstream_command` / `upstream_args` / `transport`（先只支持 stdio）
- 删掉/替换现有 `govern/proxy.py`

**关键实现点**
- MCP 的 `Tool` 对象不能直接透传，要重新包装成本地函数：`func=lambda **kwargs: await upstream.call_tool(name, kwargs)`
- 返回体要保留 `isError`、`content`、`structuredContent`，**不要只取 text**（否则 Agent 拿不到结构化结果）
- `lifespan` 里 `await stack.aclose()`，别泄漏子进程（`lab_02` 的教训：连接要成对关）

**测试 / 验收**
```powershell

python -m gate.snapshot --server examples/demo_server.py --out snapshots/direct

# 经治理层
python -m gate.snapshot --server "<govern 的启动命令占位>" --out snapshots/via-govern
# 期望：两份 tools.json 的 sha256 相同
```
> 这一步不用 Redis、不用数据库，纯转发 —— **先证明"代理不改变契约"**，这是后面所有数字的前提。

**卡住了怎么办**：`mcp` SDK 1.25 的 `FastMCP` **没有** `as_proxy`（那是独立 `fastmcp` 包），所以必须自己写"注册上游工具"这一段；先只支持 1 个工具打通，再循环注册。

### P1 · 限流（1 天）

**目标**：超阈值返回 429（JSON-RPC error，不是 HTTP 500）；Redis 挂了按配置 fail-open。

**要写**
- `govern/ratelimit.py`：令牌桶 Lua（**从 `_labs/lab_03_ratelimit_breaks.py` 直接搬**），key：`rl:{tenant}:{tool}`；另加一个租户总配额 key `rl:{tenant}`
- `govern/errors.py`：`{"jsonrpc":"2.0","id":<原 id>,"error":{"code":-32000,"message":"rate limited","data":{"retry_after":1}}}`
- HTTP 头：`Retry-After`、`X-RateLimit-Limit`、`X-RateLimit-Remaining`
- 降级：`RATELIMIT_FAIL_MODE=open|closed`（**默认必须显式选一个并写进 README**，不能"没写异常处理"）

**测试清单（`fakeredis`，不需要真 Redis）**
- 并发 40 请求、限额 10 → 恰好 10 个通过（用 `lab_03` 的 barrier 手法）
- 窗口边界：**验证令牌桶不会双倍放行**（对照 `lab_03` 里固定窗口的 2.0x）
- Redis 抛异常 → fail-open 放行且打 `warning`；`fail_mode=closed` → 拒绝
- 限额为 0 → 全部拒绝（边界）

**验收**
```powershell
python -m pytest tests/test_ratelimit.py -q     # 6+ passed
# 手工：压 10 并发，第 6 个开始拿到 429
```

> ⚠️ 三件事别做错（都是你在 `lab_03` 亲手验证过的）：
> ① 别用固定窗口（127ms 放行 2 倍限额）；② 别把 `INCR` + `EXPIRE` 拆成两条命令（拆开就超卖）；
> ③ 抄上游 Lua 时**剥掉第一行 `#!lua flags=...`**，否则普通 Redis 客户端报 `unexpected symbol near '#'`。

## 5. 中间件的正确写法（P0 的核心，最容易写错的地方）

**必须用纯 ASGI 中间件**，不能用 `BaseHTTPMiddleware`（读 body 会和响应流打架，SSE 会被卡死）。

```python
class GovernMiddleware:
    def __init__(self, app, core):
        self.app, self.core = app, core

    async def __call__(self, scope, receive, send):
        if scope["type"] != "http":
            return await self.app(scope, receive, send)

        # 1) 把请求体读完（一次），拿到 JSON-RPC
        body = b""
        while True:
            msg = await receive()
            body += msg.get("body", b"")
            if not msg.get("more_body"):
                break

        # 2) 治理：租户 → 限流 →（放行后）指标/审计 的"开始"打点
        decision = await self.core.before(scope, body)
        if decision.reject:
            return await self.core.send_reject(send, decision)   # 直接 200/HTTP 状态 + JSON-RPC error

        # 3) 重放请求体给下游（只回一次！下游若再调 receive 要自己兜住）
        replayed = False
        async def replay():
            nonlocal replayed
            if replayed:
                return {"type": "http.disconnect"}
            replayed = True
            return {"type": "http.request", "body": body, "more_body": False}

        # 4) 包一层 send，记录状态码与耗时（响应体不解析，兼容 SSE）
        status = {"code": 0}
        async def send_wrapper(message):
            if message["type"] == "http.response.start":
                status["code"] = message["status"]
            await send(message)

        try:
            await self.app(scope, replay, send_wrapper)
        finally:
            await self.core.after(decision, status["code"])      # 审计收尾 + 指标 observe
```

**三个坑**：
1. `replay()` **只能返回一次**，否则下游第二次 `receive` 会拿到空 body（表现为"代理偶发解析失败"）。
2. 拒绝时**不要用 HTTP 500**：MCP 客户端会把 500 当传输层错误；正确做法是 HTTP 200 + JSON-RPC `error`（或者 429 + 可解析体，二选一并写进 README）。
3. 响应可能是 `text/event-stream`（SSE），**不要试图完整解析响应体**；P2 的审计只记请求侧 + 状态码 + 耗时，已经够用。

## 9. 做完之后，简历/面试能说什么（都是可验证的）

1. **「治理层是协议级透明代理」**：对 Agent 是 MCP Server、对上游是 MCP Client；治理挂在 ASGI 层，所以 `tools/list` 也过闸，不只是 `tools/call`。
2. **「限流用令牌桶 + Lua，一次往返」**：固定窗口会边界双倍、`INCR`+`EXPIRE` 拆开就不原子——这两条我都在实验台测过数字。
3. **「Redis 挂了必须显式选 fail-open / fail-closed」**：不写异常处理 = 隐式 fail-closed 且没有日志，是最差的组合。
4. **「审计只存摘要」**：`args_digest` + key 列表 + 大小，明文一律不落库；合规风险来自"存全文"。
5. **「代理开销是量出来的」**：直连 p95 3.1ms vs 代理 5.4ms → +2.3ms；不测直连就没法归因。
6. **「p95 是从桶里插值出来的」**：桶太粗会偏 +50%，上限太低会把分位数钉在最后一档。

| D1 | P0 代理骨架（1 个工具） | 经代理调到工具，返回结构一致 |
| D2 | P0 收尾（全部工具 + sha256 对比） | 直连/代理 `tools.json` 完全相同 |

## 附：本方案刻意不做的事（免得你被"要不要一起做"分心）

- **不实现 MCP 协议栈**：转发全部走官方 `mcp` SDK
- **不做多副本 / 一致性哈希**：单实例 + Redis 已经把桶放到外部，扩容是"多起几个进程"的事
- **不做鉴权系统**：租户从 header 取，JWT 只留一个替换点
- **不做 Web UI**：`/metrics` + `reports/*.md` 足够
- **语义工具路由（原 M6 的最后一项）**：属于"降 token"的另一条线，等 P5 之后单独评估——它和治理不是同一件事
