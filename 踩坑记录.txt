🛠️ P0：代理骨架（协议透传与元编程）
核心目标：让你写的网关能被 Agent 无缝连接，且不改变任何原有的工具契约。

坑 1：框架的“自作聪明”（Schema 被毁）

现象：原本是 {"city": "string"}，代理一转手变成了 {"kwargs": "string"}。

原因：FastMCP 默认会根据 Python 函数的 **kwargs 动态生成 Schema，直接覆盖了上游真实的定义。

解法：利用 Python 的反射机制 inspect.Signature，伪造了一个假的 __signature__ 骗过框架。

坑 2：闭包陷阱（所有工具都变成了最后一个）

现象：调用 get_weather，结果底层执行的却是 search_doc。

原因：在 for 循环里定义异步函数，Python 的闭包会共享变量，循环结束后变量固定成了最后一项。

解法：用工厂函数（create_proxy(t_name)）把变量“锁死”在局部作用域里。

重点：区分 FastMCP（适合开发业务，会自动生成 Schema）和 Server（适合做代理，底层收发，原样透传）。

🚦 P1：高并发限流（Redis、Lua 与降级）
核心目标：防击穿，防并发超卖，防 Redis 挂掉导致全站瘫痪。

坑 1：INCR + EXPIRE 的非原子性

现象：并发 40 个请求，限额 10，结果放行了 20 多个。

原因：如果你用代码先查（GET），再判断，再写（INCR），中间的时间差足以让另外 20 个请求挤进来。

解法：把逻辑写进 Lua 脚本。Redis 单线程执行 Lua 时是原子的，中间无法插队。

坑 2：固定窗口的边界双倍放行

现象：上一秒的最后 0.1 秒放行了 5 个，下一秒的前 0.1 秒又放行了 5 个，瞬间放行 10 个。

解法：使用 令牌桶（Token Bucket）。令牌匀速补发，完美平滑突发流量。

重点：降级策略（Fail-open vs Fail-closed）。在 except 里一定要捕获 Redis 异常。Redis 挂了是放行（保业务）还是拒绝（保安全），必须在配置里显式写明，千万不能什么都不写。

📝 P2：异步审计与脱敏（SQLAlchemy、生命周期与锁）
核心目标：记录每一次调用，但绝对不能存用户隐私（PII），且不能拖慢主流程。

坑 1：SQLite 并发写入锁冲突

现象：8 个请求并发写库，只进去了 4 条。

原因：SQLite 写文件时默认加独占锁，并发写入直接报 database is locked 并被 try...except 悄悄吞掉。

解法：引入 asyncio.Lock()，让 8 个任务排队写库，彻底解决冲突。

坑 2：异步任务“幽灵丢失”（Task 被 GC 回收）

现象：代码里明明写了 create_task，查库却少了数据。

原因：create_task 返回的任务如果没有变量引用，会被 Python 的垃圾回收器直接干掉。

解法：全局维护一个 _background_tasks 集合，任务放进去，结束后用 add_done_callback 移除。

坑 3：Windows GBK 编码导致后台崩溃

现象：明明 commit 成功了，日志却报落库失败。

原因：代码里写了 print("✅ 成功")，但 Windows 终端不支持 Emoji 字符，触发 UnicodeEncodeError 直接崩溃。

解法：生产代码里不要乱打特殊字符，日志统一走 logging 模块并设置 UTF-8 编码。

重点：PII 脱敏（隐私合规）。只存参数的 Key 列表（args_keys）和 SHA-256 哈希（args_digest），绝对不存明文。
